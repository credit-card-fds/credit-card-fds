# 검토 보조 에이전트 계획

## 목표
RF 모델(임계값 0.15)이 Test에서 걸러 낸 **리뷰 큐 68건**에 대해, 에이전트가 근거를 모아 요약하고 검토 우선순위를 정한다.

| 역할 | 담당 |
|---|---|
| 판정 (사기 확률) | RF 모델 |
| 근거 수집·요약, 우선순위 | 에이전트 (도구 + LLM) |
| 최종 결정, 라벨 확정 | 사람 |

## 구조
```
credit-card-fds/agent/

├── agent.py           ⑤ LLM 에이전트 루프
```

## 1단계에서 확인한 사실 (이전 시도)
- 리뷰 큐 68건 중 실제 사기 57건 / 정상 11건 (`final_report`와 동일)
- 점수 0.7 이상 53건 중 사기 50건 → 짧은 확인으로 충분
- 점수 0.7 미만 15건 중 사기 7건 / 정상 8건 → **에이전트가 깊게 조사해야 할 구간**
- processed 데이터의 `Amount`는 log1p + RobustScaler 변환값 → 원본(`data/raw`)이 없어 유로 금액은 복원하지 않음. 도구 1은 정상 거래 대비 백분위로 크기를 알려 줌 (변환이 단조 증가라 백분위는 원래 금액과 같음)

## 한계 (미탐) — 사후 분석은 하지 않기로 함
- Test 사기 72건 중 미탐 15건. 점수: 0.10, 0.06, 0.02, 0.01, 0.005×3, 0×8 → 8건이 0점
- 임계값을 낮춰도 거의 못 잡음: 0.05 → 경보 83건 / 사기 59건, 0.01 → 경보 438건 / 사기 61건
- 결론: 임계값 문제가 아니라 **익명화된 특성 30개로는 정상과 구별되지 않는 사기**. 위치·고객 패턴 같은 정보가 필요함
- 에이전트도 같은 데이터를 보므로 이 한계를 넘지 못함 (경보 68건 검토 보조에만 집중)

## API 키 없이 진행한 검토 결과 (Claude Code가 에이전트 역할 대행, 2026-10-30)
- 방식: `review_tools.py`의 도구 4개를 그대로 실행하고, 요약·권고·우선순위는 Claude Code가 작성함. `agent.py` 루프를 실제로 실행한 결과는 아님
- 공정성: 권고를 `outputs/agent_results.csv`에 먼저 확정한 뒤 `evaluate.py`로 정답과 비교함 (라벨은 비교 단계에서 처음 사용)
- 나중에 API로 실행하면 같은 파일이 덮어써짐 → 그 결과가 이 프로젝트의 정식 결과

| 구간 | 권고 | 실제 사기 | 실제 정상 |
|---|---|---|---|
| 애매한 구간 (<0.7, 15건) | 사기 가능성 높음 | 5 | 0 |
| | 추가 확인 필요 | 1 | 4 |
| | 정상 가능성 높음 | 1 | 4 |
| 확신 구간 (≥0.7, 53건) | 사기 가능성 높음 | 49 | 2 |
| | 추가 확인 필요 | 1 | 1 |

- 우선순위 high 49건 중 사기 47건 (96%), medium 14건 중 사기 9건, low 5건 중 사기 1건 → 위에서부터 검토하면 사기를 먼저 만남
- 아낀 검토: 큐 안의 실제 정상 11건 중 4건을 "정상 가능성 높음"으로 맞게 분류
- 위험한 실수 1건 (`33573`): 가장 가까운 과거 사례가 거리 6.8로 멀었는데, "극단값이 적고 이웃 10건 중 7건이 정상"이라는 약한 근거로 정상 권고함 → "추가 확인 필요"가 맞았음
- 잘 맞은 규칙: "거리 3 이내에 정상 과거 사례가 몰려 있음" → 정상 권고 4건 모두 정답
- 놓친 정상 `26343` (0.875): 유사 사례 5건이 모두 사기이고 SHAP도 사기 쪽이라, 도구 결과로는 구별할 근거가 없었음
- 표본이 작아(애매한 구간 15건) 1건 차이로 비율이 크게 흔들림
