# 검토 보조 에이전트 계획

## 목표
RF 모델(임계값 0.10)이 Test에서 걸러 낸 **리뷰 큐 70건**에 대해, 에이전트가 근거를 모아 요약하고 검토 우선순위를 정한다.

| 역할 | 담당 |
|---|---|
| 판정 (사기 확률) | RF 모델 |
| 근거 수집·요약, 우선순위 | 에이전트 (도구 + LLM) |
| 최종 결정, 라벨 확정 | 사람 |

## 구조
```
credit-card-fds/agent/
├── CLAUDE.md          작업 규칙 (Claude Code가 자동으로 읽음)
├── PLAN.md            이 문서
├── requirements.txt   필요한 패키지
├── config.py          ① 경로, RF 설정, 임계값, 비용 가정
├── data.py            ② 데이터 로드, RF 학습·저장·불러오기
├── queue_builder.py   ③ 리뷰 큐 만들기 (라벨 없음)
├── review_tools.py    ④ 에이전트 도구 4개
├── agent.py           ⑤ LLM 에이전트 루프
├── evaluate.py        ⑥ 재현성 확인, 권고 vs 실제 라벨 평가
├── main.py            ⑦ 실행 진입점
├── app.py             ⑧ 시연 화면 (streamlit run app.py)
├── models/            rf_final.joblib (실행 시 생성)
└── outputs/           리뷰 큐, 에이전트 결과 (실행 시 생성)
```

## 1단계에서 확인한 사실 (이전 시도)
- 리뷰 큐 70건 중 실제 사기 58건 / 정상 12건 (`final_report`와 동일)
- 점수 0.7 이상 53건 중 사기 50건 → 짧은 확인으로 충분
- 점수 0.7 미만 17건 중 사기 8건 / 정상 9건 → **에이전트가 깊게 조사해야 할 구간**
- processed 데이터의 `Amount`는 log1p + RobustScaler 변환값 → 원본(`data/raw`)이 없어 유로 금액은 복원하지 않음. 도구 1은 정상 거래 대비 백분위로 크기를 알려 줌 (변환이 단조 증가라 백분위는 원래 금액과 같음)

## 한계 (미탐) — 사후 분석은 하지 않기로 함
- Test 사기 72건 중 미탐 14건. 점수: 0.06, 0.02, 0.01, 0.005×3, 0×8 → 8건이 0점
- 임계값을 낮춰도 거의 못 잡음: 0.05 → 경보 83건 / 사기 59건, 0.01 → 경보 438건 / 사기 61건
- 결론: 임계값 문제가 아니라 **익명화된 특성 30개로는 정상과 구별되지 않는 사기**. 위치·고객 패턴 같은 정보가 필요함
- 에이전트도 같은 데이터를 보므로 이 한계를 넘지 못함 (경보 70건 검토 보조에만 집중)

## 정식 결과: API 실행 (Claude Haiku 5.5, 2026-11-04)
> `python main.py --agent`로 `agent.py` 루프를 실제로 실행한 결과입니다. 아래 "Claude Code 대행" 결과는 비교용 참고 자료로 남겨 둡니다 (`outputs/backup_claude_code/`).
- 방식: 리뷰 큐 70건 전체, 모델 `claude-haiku-5-5`. 권고를 `outputs/agent_results.csv`에 먼저 저장한 뒤 `evaluate.py`로 정답과 비교함 (에이전트는 라벨을 보지 않음)
- 실행: 70건 모두 오류 없이 제출, 건당 도구 3~4회 (평균 3.8회)
- 비용: 측정한 2건이 건당 약 $0.001~0.0015 (입력 약 6천 / 출력 1~2천 토큰) → 70건 전체 약 $0.1

| 구간 | 권고 | 실제 사기 | 실제 정상 |
|---|---|---|---|
| 애매한 구간 (<0.7, 17건) | 사기 가능성 높음 | 2 | 0 |
| | 추가 확인 필요 | 5 | 9 |
| | 정상 가능성 높음 | 1 | 0 |
| 확신 구간 (≥0.7, 53건) | 사기 가능성 높음 | 50 | 3 |

- 우선순위 high 59건 중 사기 55건 (93%), medium 10건 중 사기 2건 (20%), low 1건 중 사기 1건 → 위에서부터 검토하면 사기를 먼저 만남
- **판단을 사람에게 넘기는 쪽**: 애매한 구간 17건 중 14건을 "추가 확인 필요"로 둠. 그래서 위험한 실수는 적지만, 아낀 검토는 0건 (큐 안의 실제 정상 12건 중 "정상 가능성 높음"으로 맞힌 건 없음)
- 위험한 실수 1건 (`25140`, 0.100): 정상 쪽 근거만 보여 정상 / low로 권고 → 실제 사기. 대행 결과와 같은 실수로, 합격선 근처의 사기는 도구 근거로 구별이 안 됨 (미탐 14건과 같은 성격)
- 확신 구간에서 "사기 가능성 높음"인데 정상인 3건 (`7616` 포함): 유사 사례와 SHAP가 모두 사기 쪽이라 도구 결과만으로는 구별 근거가 없음
- 대행 결과와 비교: 권고 60/70건 일치. 달라진 10건은 대부분 대행 때 "사기" 또는 "정상"이던 것이 "추가 확인 필요"로 바뀐 경우
- 한계: LLM은 실행마다 답이 조금씩 달라질 수 있음. 한 번 실행한 결과이고, 애매한 구간이 17건뿐이라 1건 차이로 비율이 크게 흔들림
